## 一、最高教训：三次著名误判的复盘

早期排障时连续给出三个错误结论，用户反驳三次才纠正。**共同根因：把"我以为"当成"已确认"。**

| 误判 | 事实 |
|---|---|
| "多实例互踩" | lsof 实查是正常的父子进程树，根本没有互踩 |
| "日志没写 Login success = 未登录" | 历史成功期日志同样没有这条记录，此日志特征不能当判据 |
| "存储满导致 NapCat 假死" | 四条命令实测 NapCat 活着、日志在写 |

**由此定下的规矩：**
1. 结论必须有实证（lsof / 实测命令 / API 回读），推断链不闭环不下结论
2. 用户反驳时，先查历史对照（"上次能用时是什么样"），再决定坚持或收回
3. 没查源码/schema 不写配置；没验证远程状态不报成功
4. 别抓一个新线索就当新原因；一个症状可能多个原因，逐一排除

## 二、铁律（违反必翻车）

1. **cmd.txt 第一行必须是任务编号（纯数字）**，第二行起才是命令。缺编号 = 循环当异常丢弃，且伪装成"API响应异常"，极易误诊为网络问题。（2026-11-01 实锤）
2. **每推必验证**：git push 会假成功（exit 0 但远程没有），含 `ghp_` 字面量的文件会被密钥扫描拦截。统一用 GitHub API PUT，推完必须 GET 回读确认。
3. **API PUT 前必先 GET sha**：直接 PUT 已存在文件会 422。
4. **在线状态绝不重启 NapCat**：logincheck 显示 [在线] 时碰都不要碰登录相关进程。
5. **保险丝**：24h 内自动拉起 NapCat ≥3 次即熔断（只报警不重启），防"崩→扫→崩"恶性循环。人工判断后的重启不受保险丝限制，但必须先看 logincheck。
6. **扫码纪律**：随用随取码，不空转出码；给用户码之前必须确认文件是新生成的（对时间戳），绝不拿旧码充数。码过期 NapCat 会自动换新码，复制到相册的旧图不会自己更新。
7. **不碰登录站稳后的 NapCat**；NapCat 挂掉多为服务端作废会话，不是进程崩。
8. **不向用户要 QQ 密码**（风控反噬+泄露面大）。
9. **手机端操作最小化**：一次最多一条可粘贴命令；能遥控做的绝不麻烦用户。
10. **先验证再让用户行动**：让用户扫码/执行前，自己这边先确认就绪。
11. **别绕路**：曾让用户试了两轮"过期跳官网"之类的歪路才承认只能扫码——先走已验证的正路。
12. **换框架不解决登录问题**：NapCat 同样要扫码。出登录问题时先修登录，别病急乱投医换协议端。
13. **一切改动以不影响运行为红线**（2026-11-01 用户明确要求）：代码优化可以做，但优化过程中任何一步只要**有可能**影响阿萨尔的正常运行，立即停止优化。执行顺序上：改动先在沙箱验证 → 确认无运行风险 → 才上手机；手机上正在跑的进程不因部署改动而重启/中断，能热替换就热替换，不能就等维护窗口并征得用户同意。

## 三、坑清单（按主题）

### 风控与登录（最贵的学费）
- **ErrCode 3 = 服务端作废会话（账号级风控）**，本地配置无解：只能时间冷却（24~48h）+ QQ 账号安全中心清设备 + 减少重启，再扫码。
- **频繁扫码/重启会加重风控**——曾让用户反复扫码反而火上浇油。登录动作是稀缺资源，一次成功就站稳。
- **新号/异地登录风控严**：固定一台设备登录，不要频繁换环境。
- **签名服务器（sign-server）必须配**：缺失会导致登录 45 错误码、发消息被风控。现用 `https://sign.lagrangecore.org/api/sign`，配置项 sign-server / sign-servers / sign-server-timeout。
- **快速登录的真相**：手机端 quickLogin 缓存有效——**凭据恢复型重启可免扫码复活，前提是登录站稳几分钟后再重启**；沙箱休眠杀进程后凭据不完整，快速登录不可靠，必须重扫。 NapCat 只支持扫码/快速登录，没有密码登录。
- **登录闪断窗口的症状**：send_msg timeout、NapCat 循环刷新二维码（扫码事件根本没被腾讯接受）→ 这是账号级风控的表现，别急着扫下一张，先等冷却。
- **二维码过期机制**：qrcode.png 过期后 NapCat 自动换新码；沙箱侧复制出来的图不会自动更新，必须重新复制并核对时间戳。

### 遥控通道
- **cmd.txt 格式**：`第一行任务号\n命令...`。主循环 `case "$RAW" in [0-9]*)` 判定，非数字开头直接丢弃。
- **out.txt 格式**：`<<<task_N.txt>>>` 打包 + 待发箱 `/root/.remote_pending` 兜底，回传失败留待下轮。
- **git 通道在手机上不可靠**："Failure when receiving data from the peer" 反复出现，API 从未失败 → 终版全 API（GET/PUT contents），git 弃用。
- **手机取 token**：不要用 `git credential fill`（无凭据存储会弹交互卡死循环），用 `grep -oE 'ghp_...' /root/.git-credentials`。
- **回传细节**（v4.1 教训）：URL 别拼成 `.../cmd.txt/out.txt`；待发箱文件必须带 `.txt` 后缀否则回传过滤掉。
- **git push"假成功"**：exit 0 但远程没有文件；内嵌 `ghp_` 字面量的文件必被密钥扫描拦截。一切以 API 回读为准。

### 进程管理
- **pgrep -f 自匹配陷阱**：`pgrep -f remote_ctl.sh` 会匹配 cmdline 含该字符串的其他命令（proot 包装命令、自己）。判定用锁文件 + `kill -0`。
- **单实例锁的坑**：重启后旧 PID 可能被其他进程占用 → `kill -0` 误判"已运行" → 新循环静默退出。人工确认无真实例后 `rm -f /root/.remote_pid` 再启动。
- **多实例清理**：反复启动会并存多实例（重复执行任务/重复拉 NapCat/保险丝计数虚高）。`for p in $(pgrep -f "bash /root/remote_ctl.sh"); do [ "$p" != "保留PID" ] && kill -9 $p; done`。
- **proot 一条式启动会被清场**：`proot-distro login ubuntu -- bash -c 'nohup ... &'` 跑完 proot 以 `--kill-on-exit` 收尾，后台循环陪葬。正确姿势：交互式进 ubuntu，nohup 启动后**不 exit**，Home 切走。
- **Ctrl+C 退出出码脚本会连坐杀死 NapCat（2026-11-02 实锤，当日事故真因）**：脚本（非交互 shell）里 `nohup xxx &` 的后台任务与脚本**同进程组**；Ctrl+C 向整组广播 SIGINT；nohup 只防 SIGHUP，而 QQ/Electron 会自行重置信号处理器，绕过 POSIX"后台任务忽略 SIGINT"的保护 → 用户 Ctrl+C 退出 azar_login.sh，NapCat 于 16:20:37 以 Electron `FATAL: Failed to shutdown` 崩溃（死亡姿势=shutdown 中被信号打断）。**沙箱四组对照实验实锤**：普通 bash 后台任务存活 / Electron 型被连坐杀 / 加 setsid 毫发无伤。**修复：一切脚本内启动 NapCat 必须加 `setsid`**。当日最初误判为"用户 exit 退出 Ubuntu 触发清场"，经用户纠正（"我没退 Ubuntu，只退了脚本"）后重新归因——用户对自己操作的描述是最优先证据，归因前先问清每一步按了什么。
- **能 grep 解决的不重启，pkill 是最后手段**。
- **竞态**：先读 `/proc/<pid>` 再 kill，中间进程可能已消失；升级瞬间新旧循环竞态会回传空文件（验证升级看下一个任务的输出，不信当次）。
- **shell 假成功**：`a && b ; echo 完成` 中 echo 必执行，别拿尾缀 echo 当成功凭证。
- **NapCat 启动方式**：proot 无显示服务，必须 `xvfb-run -a /root/Napcat/opt/QQ/qq --no-sandbox`（必要时 `-q QQ号` 走快速登录）。

### 手机后台（华为）
- **省电模式全局掐后台网络**，优先级高于单 App 白名单 → 已关，永久保持关。
- **被冻结的进程不会自动解冻**，必须重启进程（症状：进程活着、心跳为零、手动跑 API 却通）。
- 长连接（NapCat 挂机）不受影响，被掐的是周期性主动联网（遥控轮询）。
- 电池优化/自启动/wake-lock 部署时已配好，别重复建议；手机重启后 Termux **不会自启**，需手动开 App + 交互 shell 启动循环。

### 连接稳定性
- **NetworkError: WebSocket call api send_msg timeout**：反向 WS 下 API 调用超时（默认 30s），多发生在登录闪断窗口/重连瞬间，NapCat↔NoneBot 每 30 秒自动重连，网络波动自愈——先等一轮再判断，别乱动配置。
- **onebot11 配置 `websocketClients` 必须数组格式**：对象格式被 schema 静默丢弃（不报错！），症状=登录成功但 WS 不接、大脑收不到消息。用 WebUI API 查运行时配置实锤。
- WebUI 认证：POST `/api/auth/login` `{"hash": sha256(token+'.napcat')}`，Bearer 调 `/api/QQLogin/CheckLoginStatus`、`/api/OB11Config/GetConfig`。
- 登录三态权威判定：`bash /root/logincheck.sh` → [在线]/[掉线]/[未登录] + loginPhase + loginError。**日志特征不能当登录判据**（见最高教训）。
- 二维码位置：`/root/Napcat/opt/QQ/resources/app/app_launcher/napcat/cache/qrcode.png`。

### 大脑（NoneBot / 插件）
- **import 缺失会让整个模块加载中断**（如 `NameError: name 'GroupMessageEvent' is not defined`），症状像"函数缺失"，实际是模块没加载完。
- **事件规则**：群聊统一 `rule=to_me()`，注意 priority 与 block 的层级，避免事件被低优先级处理器截胡。
- **棋局超时竞态**：测试步间 2.5s×3 步 > 8s CHESS_TIMEOUT 会互相踩，超时要大于实测最慢链路。
- **业务分级**：群聊强制全年龄，私聊开放 R18——改功能时别破坏这条。
- **抓取失败不阻塞**：搜索/看图失败时走"说不准"兜底并打风控标记，绝不让插件崩或复读。
- **复读的教训**：重试逻辑没去重会风控重发导致复读。

### 模型 API（智谱 BigModel）
- **429 限流**：加冷却闸，被限流后短时间别再打同一接口；不是代码问题，别乱改代码。
- **模型返回空内容**：日志显示调用成功但 content 为空——加空回复兜底，不把空串发给群。
- **glm-4-flash 语料惯性太强**：人设必须靠 system prompt 硬约束，并在回复后处理（前后缀清洗），只改人设文字压不住。
- 换模型只改 BASE_URL 与 MODEL（智谱/豆包/月之暗面兼容同一接口形态）。
- 智谱 web-search-pro 与对话共用同一 API key，检索结果不准时要求"说不准"，不许编。

### 协议端历史（go-cqhttp → NapCat）
- go-cqhttp 时代：v1.2.0 Linux 版是 **.tar.gz 不是 .zip**（下载后解不开报格式错）；config.yml 的 sign-server 同样必配。
- 迁移 NapCat 的原因：go-cqhttp 停更、协议风控重。**但换端不解决账号风控**——登录问题归登录，别混着排查。

### 沙箱（验证场）
- 约 10 分钟空闲清后台进程；休眠杀掉 NapCat 后快速登录不可靠，大概率要重新扫码。
- 沙箱当验证场：账号能不能收发、配置对不对，先在沙箱跑通再上手机。

## 四、标准流程

### 手机重启后恢复
1. 用户打开 Termux（必须手动，无自启）
2. `proot-distro login ubuntu`（交互式进入）
3. `rm -f /root/.remote_pid; nohup bash /root/remote_ctl.sh >/dev/null 2>&1 & sleep 1; echo PID: $(cat /root/.remote_pid)`
4. **不 exit**，Home 切走
5. 遥控下发「状态检查」任务验证回传；同时查循环日志排多实例

### 扫码登录（用户说"出码"才启动）

**用户侧固定命令（2026-11-02 与用户确认，永远用这套，别换花样）**：
1. 打开 Termux → `proot-distro login ubuntu`
2. `bash ~/azar_login.sh`（自动出码，二维码存 DCIM/Camera/asar_qr.png）
3. QQ 扫相册里的 asar_qr.png
4. 成功后**按 Home 切走，永不 exit**（exit = NapCat 被清场陪葬，2026-11-02 实锤）

**一条式命令的适用边界（2026-11-02 用户追问"为什么不用以前的一条式命令"）**：
- `proot-distro login ubuntu -- bash -c '...'` 跑完即回提示符，**适用于跑完就结束的任务**（查状态、拷文件、部署插件文件）
- **严禁用于出码登录/启动长期进程**：命令跑完 proot 清场，NapCat 当场陪葬——扫码成功也白扫。用户希望"一条命令搞定出码"，正解是**遥控通道代劳**：用户说"出码"→远端启动 NapCat+保鲜循环→用户只负责扫码，一条命令都不用输

1. 遥控下发保鲜命令（相册 `Pictures/阿萨尔登录码.png` 每 20 秒更新）
2. NapCat 若未出码则人工重启出码（先看 logincheck + 保险丝状态）
3. QQ 扫一扫 → 相册选码 → 确认登录
4. 遥控跑 logincheck 验证 [在线] → 群里 @阿萨尔 测试
5. 登录成功后不再碰 NapCat；站稳几分钟前不做任何重启实验

### 下发命令的标准动作
1. PUT cmd.txt（先 GET sha；第一行任务号 = 上次 LAST+1）
2. 等 60~90 秒 GET out.txt（加时间戳参数防缓存）
3. 没回传先查循环日志（下发任务 `tail /root/remote_ctl.log`），别急着怀疑网络
4. ErrCode 3 时：不折腾本地，走"冷却 + 账号安全中心清设备 + 减少重启"路线

## 六、功能验证四层法（@功能翻车的教训，2026-11-01 定）

**翻车根因**：@ 功能第一版只单测了"转换器"环节（假设模型输出 @数字），没验证"模型听不听话"——glm-4-flash 实测旧备忘下只有 1/3 概率输出 @数字，转换器空转。且拿"编译过+单测过"当"完成"，完成标准定错了。

**今后任何新功能必须过四层才算完成：**
1. **语法层**：py_compile 通过。
2. **单元层**：核心逻辑（转换器、正则、兜底）用模拟数据穷举边界。
3. **模型行为层**（新增，最关键）：凡依赖模型输出格式的功能，沙箱里**真调模型 API**（用手机 .env 的活 key + 真实 prompt + 真实失败场景复现），多跑几次统计成功率；成功率不够就改用"不依赖模型听话"的硬保障设计（如发送端强制兜底转换）。
4. **上线首验**：部署后立即在群里定向测试（发指定消息看回复），这是只读性质的观察，无风险；通过才算闭环。

**配置事实**：手机大脑实际用智谱 glm-4-flash（.env: OPENAI_BASE_URL=bigmodel.cn, OPENAI_MODEL=glm-4-flash），历史 transcript 里的旧 key 已全部失效，以 .env 的为准。

## 七、色图多图源功能踩坑记录（2026-11-01 深夜）

### 新坑 14：沙箱测 AI 翻译环节必先注入 key 环境变量
`translate_tags()` 在模块 import 时读 `os.getenv("OPENAI_API_KEY")`——沙箱里没有 .env（.env 只在手机上），key 为空 → 请求秒失败 → 返回空串。**症状极具迷惑性：0.1 秒返回空，不像超时像代码 bug**。沙箱测任何依赖模型 API 的环节，必须 `os.environ["OPENAI_API_KEY"]=...` 在 import 之前注入（放在 nonebot.init() 前，因为 import 时就读了）。

### 新坑 15：glm-4-flash 翻译标签会"造标签"（幻觉复合词）
问"银发少女"，它造出 `silver_hair_girl` 这种**图库里根本不存在的复合标签**（正确拆分是 `silver_hair` + `1girl`），导致 tbib 搜不到 → 用户看到"未收录"。小模型幻觉是常态，双保险修复：
1. **提示词强化**：明确"禁止自造复合标签、属性必须拆分（发色/人数/服饰各自独立标签）+ 给正反例"——实测"银发少女"改为输出 `silver_hair, 1girl`。
